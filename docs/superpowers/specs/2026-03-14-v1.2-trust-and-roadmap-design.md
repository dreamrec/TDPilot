### 0d. Transport Normalization

Add to `src/td_mcp/__init__.py`:

```python
def normalize_transport(raw: str) -> str:
    """Normalize transport name: strip, lowercase, underscores to hyphens."""
    return raw.strip().lower().replace("_", "-")
```

Replace inline normalization in:

| File | Current Code | Change |
|------|-------------|--------|

| `tool_registry.py` line 136 | `TD_TRANSPORT` is stripped/lowercased but not hyphen-normalized | Apply `normalize_transport()` at module load |

**Important:** Verify which form `mcp.run()` from FastMCP accepts (`"streamable-http"` vs `"streamable_http"`). If it expects underscored, normalize for internal comparisons only and pass the SDK-expected form to `mcp.run()`. The canonical internal form is hyphenated (`streamable-http`); the SDK-facing form may differ.

### 0f. CI Bundle Integrity

New step in `.github/workflows/ci.yml` after existing checks:

```yaml
- name: Validate bundle integrity
  run: |
    uv run python -c "
    import json, sys
    from td_mcp import __version__, TOX_FILENAME
    manifest = json.load(open('mcp/manifest.json'))
    errors = []
    if manifest['version'] != __version__:
        errors.append(f'manifest version {manifest[\"version\"]} != {__version__}')
    expected_tox = f'td_component/{TOX_FILENAME}'
    if manifest['artifacts']['td_component_tox'] != expected_tox:
        errors.append(f'manifest tox path mismatch')
    if errors:
        print('\\n'.join(errors)); sys.exit(1)
    print('Bundle integrity OK')
    "
```

## Phase 1: Runtime Model (v1.2.1 — Plan Only)

### 1a. Job → Resource Notification Bridge

`JobManager.update_job()` should call `EventManager.set_state()` with URI `job://{job_id}` on every state change. This makes `td_optimize_visual` and `td_describe_dynamics` push-native instead of polling-only.

Implementation:
- `JobManager.__init__` accepts optional `event_manager` parameter
- `update_job()` calls `await event_manager.set_state(f"job://{job_id}", job_payload)` after updating
- Since `update_job` is sync, either make it async or use `asyncio.create_task` for the notification

### 1b. Resource Classification

Add `resource_mode` field to resource response payloads:
- `"pullable"` — has read-through fallback (e.g., `td://timeline/state`)
- `"subscription_fed"` — cache-only, returns `available: false` until provisioned

Add read-through fallbacks for CHOP and parameter resources where feasible.

### 1c. Subscription Keying

Change `EventManager._subscriptions` key from `path` (string) to `(path, event_type)` tuple. Update `register_subscription`, `unregister_subscription`, `get_subscription`, `list_subscriptions`, and the tool-level `td_subscribe`/`td_unsubscribe` handlers.

### 1d. Snapshot Diff Expansion

Extend `SnapshotManager.diff()` to compare:
- Connections: added/removed/changed wires
- Expressions: changed expression strings on parameters

Output adds `changed_connections` and `changed_expressions` lists alongside existing `changed_params`, `added_nodes`, `removed_nodes`.

### 1e. Vision Tool Honesty

Two options (decide at implementation time):
1. Implement basic TD-side analysis (histogram, average luminance, alpha coverage) in `mcp_webserver_callbacks.py`
2. Or rename `analyze` parameter to clearly mark it as not-yet-implemented

## Phase 2: Planning Layer (v1.2.2 — Plan Only)

### 2a. `td_preflight_patch`

New tool that validates before mutation:
- Operator type availability in current TD build
- Path conflicts (target paths already exist)
- Parameter name existence on target operator types
- Required palette/component presence

Returns structured report: `safe`, `warnings`, `blockers`.

### 2b. `td_validate_recipe`

Validates a stored technique recipe against current build/project:
- All operator types exist
- All parameter names exist on those operator types
- Referenced assets accessible
- Build compatibility check

### 2c. Recipe Lifecycle States

Add `status` field to technique store entries:
- `reference_only` — example, not for direct replay
- `candidate` — extracted but not validated
- `validated_local` — rebuilt and verified in user's environment
- `validated_portable` — verified across multiple environments
- `deprecated` — superseded or broken

## Phase 3: Knowledge Layer (v1.3.0 — Plan Only)

### 3a. `td_get_operator_doc`

Normalized operator card from TD-side introspection:
- Query `td_python_help` and `td_python_classes` on the TD side
- Return: operator name, family, summary, key parameters, common gotchas
- Optional: fetch official docs URL from `docs.derivative.ca`

### 3b. `td_get_build_compatibility`

Compare active TD build against recipe metadata:
- Output: `compatible`, `caution`, `incompatible`, `reason`
- Requires recipes to carry `td_build` metadata (added in Phase 5)

## Phase 4: TD 2025 Native (v1.3.1 — Plan Only)

### 4a. `td_python_env_status`

Inspect Python environment in running TD:
- Detect `tdPyEnvManager` presence
- Report active env path, installed packages
- Flag reproducibility risks

### 4b. `td_component_standardize`

Audit component against official palette conventions:
- Custom parameter naming
- Extension organization
- Callback setup
- Version/docs fields

## Phase 5: Memory Upgrade (v1.3.2 — Plan Only)

### 5a. Layout Metadata

Add to recipe extraction (`analyzer.py`):
- `nodeX`, `nodeY` positions
- Node color
- Comments/labels

### 5b. Build Compatibility Metadata

Add to technique store entries:
- `td_build` — TouchDesigner version at capture time
- `required_op_types` — operator types used
- `external_dependencies` — referenced external files/components

### 5c. Replay Prerequisite Validation

Before replaying a recipe:
- Check all required operator types are available
- Check external dependencies are accessible
- Produce dependency report before mutating

## CI Doctor Note

The CI step `tdpilot doctor --json --skip-td-check` checks for the .tox file on disk. In CI, the .tox binary is committed to the repo, so it will be found after the export step. If the .tox is gitignored or missing in CI, the doctor check should tolerate a `warn` on `tox_component` — this is already the behavior since CI does not run with `--strict`.
