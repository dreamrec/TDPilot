# v1.4.4 Reliability Release Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Raise the reliability floor post-v1.4.3. Turn implicit guarantees into behavioral tests, harden runtime edge cases (late-starting TD, brain-installer bitrot), unify install paths, and add CI gates that catch drift before it ships.

**Architecture:** Ten atomic items, each with a failing-test-first loop where applicable. Ordered quick-wins → tests → runtime → CI/install → mechanical format last. Items are independent — if the session times out mid-plan, partial completion is safe.

**Tech Stack:** Python 3.11+, pytest, ruff, FastMCP, uv, Node (npm plugin), GitHub Actions CI.

**Branch:** `fix/v1.4.4-reliability`

**Out of scope:** `tool_registry.py` / `mcp_webserver_callbacks.py` splits (that's v1.5.0 architecture). `_legacy.py` decomposition (same). New tools. Any TD-side (`td_component/`) changes — `API_VERSION` and `.tox` stay untouched.

**Release discipline:** bump six version fields + doc/skill headers to 1.4.3.X or 1.4.4 at the end; if any behavior changes materially, bump to 1.4.4. If it's purely additive tests + CI + docs, bump to 1.4.4 (tests are user-visible signal of correctness). Rebuild plugin zip.

**Why:** `tests/test_resource_fallbacks.py` asserts structural shape via AST. The v1.4.3 analysis (correctly) flagged that this doesn't prove the handlers *work*. The honest behavioral test is: actually call each resource handler and assert the documented payload contract (the `"mode": "static"` + `"resource_uri"` + hint-to-tool contract). The resources can't fetch live TD data because mcp>=1.3 removed context injection for parameter-less resources — that's a library constraint, not a bug. Tests should pin the contract we *actually* promise, not aspire to.

## Chunk 3: Runtime robustness

### Task 5: Lazy project-memory rebinding when TD starts late

**Why:** `tool_registry.py:247-303` derives `project_name` from TD at server startup. If TD is unreachable at boot (common during plugin install / first launch), `project_name` stays empty and both `TechniqueStore` and `PreferenceStore` are constructed with `project_name=None` — meaning every project-scoped memory call fails for the session until the user restarts the MCP server. The fix is a one-shot lazy rebind: when the first TD-reachable request lands, re-derive `project_name` and if it's non-empty, reconstruct the stores (or mutate them in place) so project scope becomes available.

**Approach:** Add `_ensure_project_scope(ctx)` similar to `_ensure_td_build(ctx)`. Cache a "tried_once" flag to avoid rebinding on every call. Call it at the top of memory tools that use project scope (`td_memory_save`, `td_memory_recall`, etc.) so the rebind is demand-driven.

**Files:**
- Modify: `src/td_mcp/tool_registry.py` (add `_ensure_project_scope`, wire into memory tools)
- Modify: `src/td_mcp/services.py` — may need `tried_project_bind: bool` field
- Test: `tests/test_memory_tools_runtime.py`

- [ ] **Step 1: Read the service container definition** (`src/td_mcp/services.py`) to understand the ServiceContainer shape and decide whether to store project_name state on it.

- [ ] **Step 2: Write failing test** in `tests/test_memory_tools_runtime.py`: simulate startup with TD unreachable (empty `project_name`), then a later memory tool call where TD is now reachable. Assert the technique store gets a valid project_name and the call succeeds.

- [ ] **Step 3: Implement `_ensure_project_scope(ctx)`**:
  - If `svc.project_name` is set, no-op.
  - Else fetch `info` from TD, derive project_name (strip `.toe`).
  - If non-empty, mutate the TechniqueStore and PreferenceStore in place (set `_project_name` and `_project_dir`, ensure dir exists).
  - Mark as tried to avoid repeating on every call.

- [ ] **Step 4: Call `_ensure_project_scope(ctx)` from the memory tools that need project scope** (`td_memory_save`, `td_memory_recall`, `td_memory_replay`, `td_memory_preferences`, etc.).

- [ ] **Step 5: Run tests** — expect pass.

- [ ] **Step 6: Commit**

```bash
git add src/td_mcp/tool_registry.py src/td_mcp/services.py tests/test_memory_tools_runtime.py
git commit -m "fix(memory): lazily bind project scope when TD becomes reachable after startup"
```

### Task 8: Install-profile unification

1. `.mcp.json` (repo default — auth required, no secret)

3. `install.ps1` (same for Windows)

## Acceptance criteria

Before declaring v1.4.4 release-ready:

1. Every item has a passing behavioral test (not AST-only) where applicable.
2. `uv run ruff check .` is clean AND `uv run ruff format --check` is clean.
3. `uv run python -m pytest` is green; coverage floor satisfied.
4. All 12 version references at 1.4.4.
5. CHANGELOG entry lists every task with user-visible framing.
6. Plugin zip rebuilt; `.tox` unchanged (no TD-side changes in this release).
7. Registry smoke: 92 / 6 / 1 (unchanged).
8. CI file passes a syntactic check (`yamllint .github/workflows/ci.yml` or equivalent).
