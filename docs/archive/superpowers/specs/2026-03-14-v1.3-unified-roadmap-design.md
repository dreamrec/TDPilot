# TDPilot v1.3 Unified Roadmap Design

**Date:** 2026-03-14
**Status:** Approved
**Scope:** Merge Track A (fix 8 open issues from improvement plan) + Track B (v1.3 blueprint new features) into 3 incremental releases.

---

## Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Track merge strategy | Merge A+B by dependency order | Some v1.3 features depend on Track A fixes |
| Knowledge deployment | Hybrid (local corpus + optional web fetch) | POPx pattern proves local works; web for freshness |
| MCP Tasks integration | Dual mode (native Tasks + JobManager fallback) | Tasks still experimental; fallback for older clients |
| Exec safety middle tier | `standard` mode: curated imports + read-only introspection | Covers 90% of real needs without security risk |
| Snapshot/restore strategy | Undo-block wrapper + expanded diff | TD's native undo is more reliable than custom rollback |
| Knowledge corpus format | Structured JSON cards | MCP tools need programmatic querying, not raw markdown |
| Versioning | Incremental v1.3.x | Each sub-release is independently shippable |

---

| Release | Codename | Focus | New Tools | Issues Fixed |

## v1.3.0 -- Knowledge Foundation

### 1. Exec Safety Middle Tier (Issue 10)

New `standard` mode between `restricted` and `full`.

**Allowed in `standard`:**
- Curated import whitelist: `json`, `math`, `re`, `datetime`, `collections`, `itertools`, `functools`, `copy`, `textwrap`, `string`, `random`, `decimal`, `fractions`, `statistics`
- Read-only introspection: `dir()`, `type()`, `isinstance()`, `hasattr()`, `getattr()`
- All existing TD API access (`op()`, `ops()`, `project`, `app`, etc.)

**Still blocked in `standard`:**
- `open()`, `__import__()`, `exec()`, `eval()`, `compile()`
- `os`, `sys`, `subprocess`, `socket`, `importlib`, `pathlib`
- `setattr`, `delattr`, `__subclasses__`, `__bases__`, `globals`, `locals`

**Implementation -- both sides:**

MCP server (`tool_registry.py`):
- Add `standard` to `_normalize_exec_mode()` valid set
- Update `_restricted_exec_violation()`: if mode is `standard`, check imports against whitelist instead of blanket blocking; allow read-only introspection tokens
- Update `_build_exec_globals()`: if mode is `standard`, pre-import whitelisted modules into exec namespace

TD side (`mcp_webserver_callbacks.py`):
- Mirror the same logic in `_restricted_exec_violation()`
- Update `_build_exec_globals()` to pre-import whitelisted modules
- Add `standard` to the valid mode set in `DEFAULT_EXEC_MODE` check

**Files:** `src/td_mcp/tool_registry.py`, `td_component/mcp_webserver_callbacks.py`

### 2. Capability Model Expansion (Issue 3)

Expand `CapabilitySet` dataclass from 5 to 10 fields:

```python
@dataclass(frozen=True)
class CapabilitySet:
    # Existing
    supports_resources: bool = False
    supports_subscriptions: bool = False
    supports_sampling: bool = False
    supports_sampling_tool_calls: bool = False
    supports_streamable_http: bool = False
    # New
    supports_tasks: bool = False
    supports_elicitation: bool = False
    transport_type: str = "stdio"
    mcp_sdk_version: str = ""
    td_build: str = ""
```

Detection:
- `supports_tasks`: probe `client_capabilities` dict for `tasks` key; default `False` if absent (MCP Tasks are experimental in SDK 1.26.0)
- `supports_elicitation`: default `False` — no reliable detection path in SDK 1.26.0; will be enabled when SDK exposes a capability flag
- `transport_type`: from `TD_MCP_TRANSPORT` (already normalized)
- `mcp_sdk_version`: from `importlib.metadata.version("mcp")` — computed once at module load, not per-request
- `td_build`: populated once at server startup via an async `td_get_info` call during lifespan init (stored on ServiceContainer, NOT on the frozen dataclass). Passed into `CapabilitySet` constructor from cached value.

Update `to_dict()` return type from `dict[str, bool]` to `dict[str, Any]` to accommodate string fields.

Update `td_get_capabilities` to return expanded set. `td_describe_surface` (tool 71) is a superset that includes capability flags plus tool/resource counts — `td_get_capabilities` remains for backwards compatibility.

**Files:** `src/td_mcp/capabilities.py`, `src/td_mcp/server.py`, `src/td_mcp/tool_registry.py`

### 3. Resource Semantics Fix (Issue 5)

Classify each resource template:

| Resource | Mode | Read-through fallback |
|----------|------|-----------------------|
| `td://timeline/state` | authoritative | Already has pull fallback |
| `td://chop/{path}/{channel}` | cache | Add: one-shot `chop_data` call |
| `td://par/{path}/{name}` | cache | Add: one-shot `get_params` call |
| `td://cook/{path}` | cache | Add: one-shot `cooking_info` call |
| `td://error/{path}` | cache | Add: one-shot `get_errors` call |
| `td://top/{path}/frame` | cache | No fallback (requires capture) |
| `td://job/{job_id}` | authoritative | Already reads from JobManager |

Implementation:
- Add `mode` field to every resource response payload
- In each cache resource handler, if state dict has no cached value, attempt a one-shot TD API call
- Key subscriptions by `(path, event_type)` tuple in EventManager instead of just `path`

**Files:** `src/td_mcp/tool_registry.py`, `src/td_mcp/events/event_manager.py`

### 4. Knowledge Corpus Infrastructure

**New package:** `src/td_mcp/knowledge/`

**Provenance metadata (attached to every knowledge response):**

```json
{

  "fetched_at": "ISO or null",

  "td_build": "2025.32460",
```

**Web fetcher (optional, opt-in via `TD_MCP_WEB_FETCH=true` env var):**
- `fetch_operator_page(op_type)` -- scrape docs.derivative.ca/OpType page
- `fetch_release_notes(build)` -- scrape release notes
- Results normalized into card schema, cached locally in `~/.tdpilot/cache/cards/`
- Freshness rules: invalidate release cards when TD build changes; operator cards stale after 90 days
- Error handling: 5s timeout, no retries, fall back to local card on any failure
- Rate limiting: max 1 request per second to docs.derivative.ca
- When `TD_MCP_WEB_FETCH` is not set or `false`, all knowledge tools use local cards only

**Card index:**
- `search(query, card_types=None, family=None)` -- text search across all cards, returns ranked
- `get_operator(op_type)` -- exact lookup
- `get_palette(component_name)` -- exact lookup
- `get_release(build)` -- exact lookup
- `check_compatibility(op_type, current_build)` -- compare build_relevance

### 7. Snapshot Improvements (Issue 7)

**Expanded diff in `snapshot_manager.py`:**

Current diff compares: changed params, added/removed nodes.

Add:
- Connection changes: `added_connections[]`, `removed_connections[]`, `rewired_connections[]`
- Expression changes: `added_expressions[]`, `removed_expressions[]`, `modified_expressions[]`

**Undo-block discipline:**

New helper:

```python
async def _with_undo_block(td_client, label, async_fn, *args):
    await td_client.request("project/lifecycle",
        {"action": "start_undo_block", "label": label})
    try:
        result = await async_fn(*args)
        return result
    finally:
        await td_client.request("project/lifecycle",
            {"action": "end_undo_block"})
```

Note: TD-side uses `start_undo_block` (not `begin_undo_block`) per `mcp_webserver_callbacks.py` line 1851.

Apply to: `td_create_macro`, `td_memory_replay`, `td_restore_snapshot`, future plan execution.

**Update `td_restore_snapshot` description** to clearly state it restores parameter values only; structural rollback uses TD native undo.

**Files:** `src/td_mcp/memory/snapshot_manager.py`, `src/td_mcp/tool_registry.py`

### 8. Planning and Validation Tools (4 new)

| # | Tool | Input | Output |
|---|------|-------|--------|
| 72 | `td_plan_patch` | `intent: str`, `target_path: str`, `recipe_id: str?` | Structured plan: `steps[]`, `dependencies[]`, `risks[]`, `validation_checks[]` |
| 73 | `td_preflight_patch` | `plan: dict` (from td_plan_patch) | `safe: bool`, `warnings[]`, `blockers[]` |
| 74 | `td_validate_recipe` | `recipe_id: str` OR `recipe: dict` | `valid: bool`, `missing_ops[]`, `invalid_params[]`, `build_compatible: bool` |
| 75 | `td_audit_project` | `root_path: str?` (default `/project1`) | Structure summary, palette usage, custom COMPs, fragile zones, build warnings |

**`td_plan_patch`:** This tool is primarily a **structured-output formatter** for the LLM's reasoning, not an independent planning engine. The LLM provides the intent and target path; the tool inspects the current state via TD API, looks up referenced operator types in the knowledge card index to verify they exist and get key param info, then returns a structured plan object that the LLM or `td_preflight_patch` can validate. The tool does NOT do NLP or generate novel plans — it structures and validates what the LLM proposes. Does NOT mutate.

Example flow:
- Input: `intent="Add feedback loop with noise displacement"`, `target_path="/project1/effects"`
- Tool inspects `/project1/effects` children, checks `feedbackTOP` and `noiseTOP` cards exist
- Output: `steps: [{create feedbackTOP}, {create noiseTOP}, {connect 0->0}]`, `risks: ["feedback loop may cause infinite cook"]`, `validation_checks: ["td_get_errors after creation"]`

**`td_preflight_patch`:** Take plan, verify each step (op types exist, paths writable, no name conflicts, params valid). Return safety assessment.

**`td_validate_recipe`:** Check all required_op_types against td_list_families, param names against knowledge cards, build_relevance against current build, external asset references.

**`td_audit_project`:** Walk project tree, identify palette components, custom COMPs, errors, heavy cook times. Return structured report.

**Files:** `src/td_mcp/tool_registry.py`, `src/td_mcp/knowledge/card_index.py`

### 9. Tutorial-to-Recipe Pipeline

Enhancement to existing technique store.

**New recipe states:**
- `reference_only` -- from docs/tutorial, never tested
- `candidate` -- structured, not yet validated
- `validated_local` -- rebuilt and passed error checks
- `validated_portable` -- confirmed cross-project
- `deprecated` -- previously valid, now fails

**New fields in technique entry:**

```json
{
  "state": "candidate",
  "validation_result": {
    "status": "pass | fail | untested",
    "validated_at": "ISO",
    "td_build": "2025.32460",
    "errors": [],
    "warnings": []
  }
}
```

**Auto-validation in `td_memory_replay`:** After replay, run `td_get_errors` on subtree. If clean, auto-promote `candidate` to `validated_local`.

**Files:** `src/td_mcp/memory/technique_store.py`, `src/td_mcp/tool_registry.py`

## v1.3.2 -- TD 2025 Native + Vision + Memory

### 10. Vision Diagnostics (Issue 6)

**Split into two honest tools:**

| # | Tool | Input | Output |
|---|------|-------|--------|
| 76 | `td_capture_frame` | `path: str`, `quality: float?`, `confirm: bool` | Frame metadata + optional base64 |
| 77 | `td_analyze_frame` | `path: str`, `modes: list[str]` | Analysis results per mode |

**Analysis modes:**

| Mode | Output |
|------|--------|
| `histogram` | 8-bin RGB distribution |
| `luminance` | Average, min, max brightness |
| `alpha_coverage` | % non-zero alpha pixels |
| `color_dominant` | Top 3 dominant colors |
| `roi_diff` | Change % between two captures in a region |

**TD-side implementation:** New `/api/analyze_frame` endpoint. Uses numpy for pixel math. Analysis runs where the pixels are -- no base64 transfer needed.

**Existing tools:** `td_capture_and_analyze` becomes convenience wrapper. Remove aspirational `auto_analyze` stub from `td_monitor_visual`.

**Files:** `src/td_mcp/tool_registry.py`, `td_component/mcp_webserver_callbacks.py`

### Seed Corpus (v1.3.0 prerequisite for v1.3.1 planning tools)

v1.3.0 must ship with a minimum viable card set so v1.3.1 planning tools have data to validate against:

- **Operators:** At minimum, cards for the ~30 most commonly used ops (noiseTOP, feedbackTOP, compositeTOP, switchTOP, selectCHOP, timerCHOP, etc.) plus all ops used in built-in macro templates
- **Palette:** Cards for the 6 key palette components (callbacksHelper, threadManagerClient, tdPyEnvManager, logger, standardization, info)
- **Release:** Card for current build 2025.32460
- **Snippets:** Summary cards for CHOP, TOP, SOP, and POP snippet families

A build script (`scripts/build_seed_corpus.py`) should generate skeleton cards from TD introspection that can then be manually enriched.

## What Is NOT in v1.3

- Full structural restore (deferred to v1.4 if undo-blocks prove insufficient)
- MCP v2 SDK migration (staying on v1.x)
- MCP Apps extension (interesting but not essential yet)
- Remote/multi-user deployment
- Embedding-based knowledge search (JSON cards + text search is sufficient)
- GeoCOMP/Nav tools (no significant TD 2025 changes found in this area)
