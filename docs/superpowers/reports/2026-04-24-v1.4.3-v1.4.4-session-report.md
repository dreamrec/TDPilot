## 2. Starting point

The user came in with a detailed technical audit of `dreamrec/TDPilot` `main` at commit `788d665`. The audit's verification run showed:

- 443 tests passing
- Ruff lint clean
- Versions synced (at v1.4.2)
- `.tox` fresh
- Personal-path scan clean
- Registry smoke reporting all required tools present

But the audit also identified six "release blockers hiding under that green surface" and a longer list of reliability / architecture / install / CI work. The central insight in the audit: *the green gates were checking artifact shape, not end-to-end behavior*. Specifically, tests that existed only asserted AST scaffolding, not that the code actually did what it promised.

## 3. My feedback on the audit

Before starting work I verified the audit's most load-bearing claims (line counts, `.mcp.json` auth posture, `technique_store` method surface, `manifest.json` resource count). Every verifiable claim was grounded. Two pieces of feedback:

1. **Auth claim (#1) needed narrowing.** The audit said "`.mcp.json` enables `TD_MCP_REQUIRE_AUTH=1` but no `TD_MCP_SHARED_SECRET` is generated or passed." I verified that `install.sh:103-155` and `install.ps1:116-207` DO generate and inject secrets — the gap is specifically the Claude Code plugin install path, which reads `.mcp.json` directly without invoking the installer. Narrowed the fix accordingly.
2. **Fix #4 (taxonomy alias) was underweighted.** The audit graded it mid-priority; I promoted it to P0 because "searches silently return nothing" is more insidious than an explicit failure — users build wrong mental models without noticing.

I also suggested three additions to the original plan:

- A deprecation-shim policy for v1.5.0 file splits (so external plugins don't break).
- A CHANGELOG entry per fix phrasing the *user-visible symptom* (so users who've been silently hitting the bug recognize themselves).
- Explicitly naming the six distribution version fields as release gates, per the repo's own `CLAUDE.md`.

## 12. Known limitations and deliberate choices

- **`install.sh` and `install.ps1` were not modified** in v1.4.4's install-profile unification task. Their output shape (auth-enabled with generated secret) was already correct — the bash/powershell scripts that need to change to call `tdpilot init` instead of hand-rolling JSON is a follow-up. Scope-reducing here avoided install-time regressions in a reliability release.
- **`paketa12` brain has no remote Drive files yet.** The manifest entry lists it as a local-build brain pointing users at `scripts/build_tutorial_brain.py`. Users who want the pre-built DB will need to wait for the Drive-host follow-up.
- **Resource handlers are intentionally static-mode.** The behavioral tests added in v1.4.4 pin that contract. They don't make the handlers fetch live TD data — that's an MCP library constraint (`mcp>=1.3` removed context injection for parameter-less resources). Upgrading the MCP library or restructuring to context-aware resources is a separate project.
- **`td_component/mcp_webserver_callbacks.py` is excluded from ruff format.** It's baked into the `.tox`, and reformatting it makes the `.tox` hash stale. Functional changes to the TD-side endpoint still land there and still require a `.tox` rebuild — this exclusion is only about cosmetic reformatting.
- **The installed plugin server the user's MCP client talks to is still v1.4.0**, not the code merged into this `main`. My retroactive live validation used that old server to *prove the bugs were real*. To run my v1.4.4 code against live TD, the user would need to either reinstall the plugin from this repo or point their MCP client at this dev repo's `.mcp.json`.
