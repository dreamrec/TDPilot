**Status:** Design approved, ready for implementation planning
**Author:** Brainstormed with the user, April 24, 2026
**Phase of:** [v1.5.0 execution plan](../plans/2026-04-24-v1.5.0-execution-plan.md) — Chunk 4

## 1. Goal

Add a first-class `td_patch_*` tool family that wraps multi-step creative TD edits in a **plan → preview → apply → validate** workflow. The tools expose typed models (`PatchPlan`, `PatchOperation`, `PatchResult`, `PatchVariant`, `ValidationReport`, `ValidationPlan`) that compose into atomic, undo-safe patch sessions — the unit of creative iteration in TDPilot.

**Success criteria:**

- 5 new MCP tools: `td_patch_plan`, `td_patch_preview`, `td_patch_apply`, `td_patch_validate`, `td_patch_variations`.
- Zero breakage of the 92 existing tools. Tool count: **92 → 97**.
- Existing `td_plan_patch` / `td_preflight_patch` remain (as compat shims over the new typed layer). Their external dict shapes are unchanged.
- Unit tests at three layers (~46 new tests); baseline 596 → target ~642 passing.
- One live-TD smoke script verifying undo-block correctness end to end.
- No schema drift for the other 92 tools (snapshot stays green).

## 2. Architecture

### 2.1 File layout

```
src/td_mcp/
├── models/
│   └── patch.py              ← NEW: PatchPlan, PatchOperation, PatchResult,
│                                    PatchVariant, ValidationPlan, ValidationReport
├── patch/                    ← NEW: internal business logic package
│   ├── __init__.py           ← public facade: build_plan, preview, apply,
│                                    validate_target, generate_variants
│   ├── planner.py            ← build_plan(intent|recipe|operations → PatchPlan)
│   ├── applier.py            ← apply_plan(client, plan, sentinel → PatchResult)
│   ├── validator.py          ← validate_target(client, ValidationPlan → ValidationReport)
│   ├── variants.py           ← generate_variants(plan, n, strategies → [PatchVariant])
│   └── undo_sentinel.py      ← UndoBlockSentinel class (MCP-free; see §2.2)
└── registry/
    ├── tools_patch.py        ← NEW: 5 @mcp.tool entrypoints; delegate to patch/*
    └── tools_planning.py     ← MODIFIED: td_plan_patch/td_preflight_patch become
                                    thin shims over patch.build_plan/preview
```

### 2.2 Dependency rules

- `src/td_mcp/patch/*` — **MCP-free.** Only imports from `models/patch.py`, `td_client`, `errors.py`. No `mcp.server.fastmcp` imports, no `Context`. Unit-testable in plain async Python with a fake TD client.
- `src/td_mcp/registry/tools_patch.py` — MCP-only wrapper. Follows the existing intentional-cycle pattern (`from td_mcp import tool_registry as _tr`). Each tool is a thin wrapper that deserializes inputs, calls into `patch/*`, and wraps the return in the standard envelope.
- `src/td_mcp/registry/tools_planning.py` — modified legacy shim. Internal implementation now delegates to `patch.build_plan()`; external dict shapes (`td_plan_patch` / `td_preflight_patch` returns) are preserved byte-for-byte so existing callers see no change.

**Dependency injection for the undo-block sentinel.** `patch/*` must stay MCP-free, but the sentinel (`_active_undo_blocks: set[str]`) lives on the MCP side. The `apply_plan()` and `build_plan()` functions accept a `sentinel: UndoBlockSentinel` parameter — a small pure-Python object with `is_active() -> bool`, `mark_active(label: str) -> None`, and `mark_inactive() -> None` methods. The MCP tool wrapper (`tools_patch.py::td_patch_apply`) reads a module-level `_SENTINEL` instance from `tool_registry.py` and passes it in. Tests construct their own `UndoBlockSentinel()` instance. This keeps the `patch/*` package free of any globals or MCP state while preserving the cross-tool sentinel contract.

```python
# src/td_mcp/patch/undo_sentinel.py — lives in patch/ so unit tests can use it
class UndoBlockSentinel:
    def __init__(self) -> None:
        self._active: str | None = None
    def is_active(self) -> bool: return self._active is not None
    def mark_active(self, label: str) -> None:
        if self._active is not None:
            raise RuntimeError(f"sentinel already active: {self._active!r}")
        self._active = label
    def mark_inactive(self) -> None: self._active = None
    @property
    def active_label(self) -> str | None: return self._active
```

The single process-wide instance lives in `tool_registry.py` (e.g. `_PATCH_SENTINEL = UndoBlockSentinel()`) and gets injected by each MCP tool wrapper.

### 2.3 Architecture approach chosen

**Approach 3 (progressive)** from brainstorming: standalone `patch/` package + dedicated `tools_patch.py` + legacy shims. Decision rationale:
- Three clean testing seams (models / logic / wiring).
- Phase 4 recipes slot under `src/td_mcp/patch/recipes/` without disturbing tools.
- Matches Phase 2's module-split pattern.
- Each module stays small (< 200 lines to start, < 400 is the warning threshold).

**Rejected alternatives:**
- *Approach 1 (pure package):* same as chosen, but without the commitment to keep files small; flagged as risk without the discipline.
- *Approach 2 (inline in tools_patch.py):* mixes MCP wiring with logic; kills the unit-test seam; leaves a 600-line file.

## 3. Relationship to existing tools

### 3.1 Decision: Layer on top (Option B from brainstorming)

The new tools do NOT supersede the existing `td_plan_patch` / `td_preflight_patch`. Instead:

- Existing tools keep their names, signatures, and return dict shape.
- Internally, they call `patch.build_plan(...)` and `patch.preview(...)` and then format the result into the legacy dict.
- Zero caller-side changes (skills, memory replays, user scripts continue to work).

**Why not supersede (Option A):** immediate breakage for zero architectural payoff. The existing names are referenced in recipes, skills, and memory replays — renaming would cascade through several artifact layers.

**Why not cohabit (Option C):** having two parallel "plan" concepts at different abstraction levels confuses future contributors. One canonical internal representation (the typed `PatchPlan`) with two presentation layers (legacy dict + new typed API) is cleaner.

### 3.2 Concrete shim example (`td_plan_patch` after refactor)

```python
@mcp.tool(name="td_plan_patch")
async def td_plan_patch(
    ctx: Context,
    intent: Annotated[str, Field(..., min_length=1, description="...")],
    target_path: Annotated[str, Field(default="/project1", description="...")] = "/project1",
    recipe_id: Annotated[str | None, Field(default=None)] = None,
) -> dict[str, Any]:
    """(unchanged docstring)"""
    finish = _tr._start_tool(ctx, "td_plan_patch")
    try:
        plan = await patch.build_plan(
            td_client=_tr._get_client(ctx),
            target_root=target_path,
            intent=intent,
            recipe_id=recipe_id,
            technique_store=_tr._get_technique_store(ctx),
        )
        legacy_dict = _legacy_plan_dict(plan)  # translates PatchPlan → old shape
        _tr._audit_log(ctx, "td_plan_patch", {"intent": intent, "target_path": target_path})
        return {"success": True, "plan": legacy_dict}
    except Exception as exc:
        _tr._record_tool_error(ctx, "td_plan_patch")
        return {"error": str(exc)}
    finally:
        finish()
```

The `_legacy_plan_dict()` helper produces exactly the shape the existing v1.4.x callers expect — the critical detail that this refactor is behavior-neutral for the old surface.

## 4. Data models (`src/td_mcp/models/patch.py`)

### 4.1 `PatchOperation`

```python
class PatchOperation(BaseModel):
    model_config = ConfigDict(extra="forbid")
    kind: Literal["create_node", "set_params", "connect", "layout", "annotate", "macro"]
    target: str | None = None   # existing path (set_params/layout) or parent path (create_node/macro)
    args: dict[str, Any]         # kind-specific; shape validated at apply time
    depends_on: list[int] = Field(default_factory=list)  # metadata only in v1.5.0
```

**`args` as untyped dict (key decision).** Pydantic discriminated unions across 6 op-kinds would produce 6 sub-models and ~150 lines of ceremony. The simpler `args: dict` trades compile-time type safety for a 6× smaller surface. Mitigated by runtime `_validate_args()` in the applier (see §6.1). Graduate to discriminated unions in v1.6.0 if the dict approach proves painful.

**`depends_on` is metadata only in v1.5.0.** The applier runs operations strictly in list order. Field reserved so future versions can add parallelism or reordering without a schema change.

**Op kind set — minimal for v1.5.0.** Six kinds. Destructive kinds (`delete`, `disconnect`) deferred to v1.5.1 once the apply/undo flow is battle-tested. This is the **two-tier** decision from brainstorming.

### 4.2 `ValidationPlan`

```python
class ValidationPlan(BaseModel):
    model_config = ConfigDict(extra="forbid")
    target_root: str                              # subtree to audit
    capture_frames: list[str] = Field(default_factory=list)  # TOP paths → frame capture
```

### 4.3 `PatchPlan`

```python
class PatchPlan(BaseModel):
    model_config = ConfigDict(extra="forbid")
    id: str = Field(default_factory=lambda: str(uuid.uuid4()))
    intent: str | None = None
    target_root: str
    source: Literal["intent_heuristic", "recipe", "operations", "variant"]
    source_recipe_id: str | None = None
    operations: list[PatchOperation]
    required_ops: list[str] = Field(default_factory=list)
    risk_flags: list[str] = Field(default_factory=list)
    undo_label: str
    validation_plan: ValidationPlan
    created_at: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
```

**Statelessness.** `id` is a correlation UUID for audit logs only. No server-side store, no TTL, no GC. Plans pass by value. Rejected: a `PatchSessionStore` with lifetime management — zero immediate benefit, non-trivial subsystem to write.

**`source` provenance tag.** Every plan carries its origin for debugging and audit. When the LLM asks "why does this plan have operations I didn't ask for?", the answer is in `source` + `source_recipe_id`.

**`risk_flags` — static flags computed at plan time.** Examples: `"mass-change"` (>20 ops), `"affects-root"` (target_root == "/"), `"unknown-op-types"` (any op references an op_type missing from the knowledge corpus). `td_patch_preview` adds live-state flags to a separate `live_risk_flags` field.

### 4.4 `PatchPreview`

```python
class PatchPreview(BaseModel):
    model_config = ConfigDict(extra="forbid")
    plan_id: str                                       # echo from source PatchPlan
    summary: str                                       # human-readable one-liner
    risk_flags: list[str] = Field(default_factory=list)         # static flags from the plan
    live_risk_flags: list[str] = Field(default_factory=list)    # live-state observations (target-missing, name-conflict, external-nested-block)
    required_ops: list[str] = Field(default_factory=list)       # op_types referenced; "unknown:<type>" prefix for missing cards
    op_count: int
```

Returned by `td_patch_preview`. Keeping the preview as its own typed model (rather than a flat dict) matches the model-return convention used by the other four tools and makes the preview schema diff-auditable alongside the rest.

### 4.5 `ValidationReport`

```python
class ValidationReport(BaseModel):
    model_config = ConfigDict(extra="forbid")
    target_root: str
    errors: list[dict[str, Any]] = Field(default_factory=list)
    cook_stats: dict[str, Any] = Field(default_factory=dict)
    frames: dict[str, str] = Field(default_factory=dict)  # path → base64 JPEG
```

### 4.6 `PatchResult`

```python
class PatchResult(BaseModel):
    model_config = ConfigDict(extra="forbid")
    plan_id: str
    status: Literal["clean", "warnings", "broken"]
    applied_ops: list[int] = Field(default_factory=list)
    failed_op: int | None = None
    failed_reason: str | None = None
    created_paths: list[str] = Field(default_factory=list)
    changed_params: list[dict[str, Any]] = Field(default_factory=list)
    connections_made: list[tuple[str, str]] = Field(default_factory=list)
    validation: ValidationReport | None = None
    risk_flags: list[str] = Field(default_factory=list)  # runtime-observed flags, e.g. "external-nested-block"
    before_snapshot_id: str | None = None   # reserved for v1.5.1 auto-snapshot
    after_snapshot_id: str | None = None    # reserved for v1.5.1 auto-snapshot
    undo_label: str
    rollback_hint: str | None = None
```

**`risk_flags` on `PatchResult`.** Distinct from `PatchPlan.risk_flags` (static, computed at plan time) and `PatchPreview.live_risk_flags` (live-state observations at preview time). `PatchResult.risk_flags` records runtime-observed flags during apply — specifically `"external-nested-block"` when the applier detected an externally-opened undo block (see §6.3). Empty in the happy path.

**`before/after_snapshot_id` reserved, default None in v1.5.0.** Snapshots are expensive (full scene copy) — auto-snapshotting every apply would be costly on large projects. Callers take explicit snapshots via `td_snapshot_scene` if they want pre/post state. Fields exist so v1.5.1 can add auto-snapshot without a schema change (matches the deferral list in §10).

### 4.7 `PatchVariant`

```python
class PatchVariant(PatchPlan):
    source: Literal["variant"] = "variant"   # narrowed from parent's 4-tuple
    base_plan_id: str
    strategy: Literal["param_jitter", "operator_substitute", "topology_perturb"]
    seed: int
```

**Inheritance over composition.** A `PatchVariant` IS a `PatchPlan` — the applier runs it unchanged. No adapter layer needed. The three extra fields record variation provenance for replay/debugging.

### 5.3 `td_patch_apply`

```python
@mcp.tool(name="td_patch_apply")
async def td_patch_apply(
    ctx: Context,
    plan: Annotated[dict[str, Any], Field(description="PatchPlan dict to execute")],
    label: Annotated[str | None, Field(default=None, description="Override plan.undo_label")] = None,
    auto_validate: Annotated[bool, Field(default=True, description="Run validation after apply")] = True,
) -> dict[str, Any]:
    """Apply a PatchPlan in one undo block. Surface-to-caller on failure (no auto-rollback)."""
```

**Envelope vs. outcome distinction:**
- Tool-level errors (malformed plan, nested undo block, TD unreachable): `{success: False, error: "..."}`.
- Patch-level outcomes: `{success: True, result: <PatchResult>}` where `result.status` carries the patch status (`clean | warnings | broken`).

This distinction ensures the LLM can trust `success=False` as an unambiguous wire/infra failure, separate from "the patch ran but didn't produce a clean outcome."

## 6. Control flow

### 6.1 `td_patch_plan` internal dispatch

`patch.build_plan()` branches on which input was provided, in strict precedence order:

```
if operations:   source = "operations"       ops = [PatchOperation.model_validate(o) for o in operations]
elif recipe_id:  source = "recipe"           ops = _recipe_to_operations(store.get(recipe_id), target_root)
elif intent:     source = "intent_heuristic" ops = _intent_to_operations(intent, target_root)  # reuses _INTENT_MACRO_KEYWORDS
else:                                        raise ValueError(...)
```

After operations are determined, compute:
- `required_ops`: collected `op_type` strings from all `create_node` ops; unknown types (not in knowledge corpus and not in `_STOCK_OP_TYPES` allowlist) prefixed with `"unknown:"`.
- `risk_flags`: static analysis over ops + target_root.
- `undo_label`: `label` override > derived from intent > `"td patch at {target_root}"` default.

### 6.2 `td_patch_apply` flow

The MCP tool wrapper (`registry/tools_patch.py::td_patch_apply`) owns the tool-level error envelope. The applier (`patch/applier.py::apply_plan`) owns the patch-level outcome. Split:

**Wrapper responsibilities** (in `td_patch_apply` wrapper):
```
try:
  plan = PatchPlan.model_validate(plan_dict)        # may raise ValidationError
except ValidationError as exc:
  return {"success": False, "error": f"invalid plan: {exc}"}
try:
  result = await patch.apply_plan(td_client, plan, sentinel=sentinel, label=label, auto_validate=auto_validate)
except NestedBlockError as exc:
  return {"success": False, "error": str(exc)}
except TDConnectionError as exc:
  return {"success": False, "error": f"TD unreachable: {exc}"}
return {"success": True, "result": result.model_dump()}
```

**Applier responsibilities** (`apply_plan(td_client, plan, *, sentinel, label=None, auto_validate=True) → PatchResult`):
```
1. Guard:  if sentinel.is_active(): raise NestedBlockError
           sentinel.mark_active(label or plan.undo_label)
2. Start:  async with _with_undo_block(td_client, label or plan.undo_label):
             try:
3. Loop:       for i, op in enumerate(plan.operations):
                 try:
                   _validate_args(op)              # kind-specific, see §6.4
                   outcome = await _apply_op(td_client, op)
                   _record_outcome(result, i, outcome)
                 except Exception as exc:
                   result.failed_op = i
                   result.failed_reason = str(exc)
                   break                            # stop; undo block still seals via finally
             finally:
               sentinel.mark_inactive()
4. Status: _compute_status(result) → "broken" if failed_op else "clean"
5. Hint:   if status == "broken":
             result.rollback_hint = f"call td_project_lifecycle action=undo to revert {len(result.applied_ops)} ops"
6. Val:    if auto_validate and status != "broken":              # skip on broken — state is mid-corrupt
             result.validation = await validate_target(client, plan.validation_plan)
             if status == "clean" and not result.validation.ok:
               status = "warnings"      # promotion rule
7. Return result
```

**Key invariants:**
- Apply stops on first failure (no best-effort continuation). TD's undo stack sees one atomic unit, reversible with one Ctrl-Z.
- `end_undo_block` runs in `_with_undo_block`'s `finally` — even on exception, the undo block seals.
- Validation status promotion: `clean` → `warnings` if auto-validate finds errors post-apply. Callers trust `status == "clean"` as a strong signal.

### 6.3 Nested-undo-block detection

**Decision: Python-side sentinel for v1.5.0**, via the `UndoBlockSentinel` class declared in §2.2. The MCP tool wrapper reads the module-level `_PATCH_SENTINEL` from `tool_registry.py` and passes it to `apply_plan(..., sentinel=...)`. The applier's first action is `sentinel.is_active()` — raises `NestedBlockError` if true, otherwise calls `sentinel.mark_active(label)`. A `finally` block calls `sentinel.mark_inactive()` regardless of outcome.

This catches blocks started by our own applier (the common case: a prior `td_patch_apply` that crashed between start and end of its own block and left the sentinel set — though `finally` makes that edge case unlikely).

**Limitation:** external undo blocks (opened by other tools like `td_component_standardize` with `fix=True`, or by the user in the TD UI) are invisible to our sentinel. In that case, our `start_undo_block` call coalesces into the existing block (TD's default nesting behavior) and the user gets one big undo step — merging our patch with their prior work. `PatchResult.risk_flags` records `"external-nested-block-possible"` whenever our apply completes without first seeing an inactive sentinel confirmation (i.e., if any `td_get_state_vector` probe ever reports an external-block hint, we flag).

**v1.5.1 follow-up:** add a `project/lifecycle action=undo_block_status` endpoint to the TD-side callback. That exposes live state and lets us refuse externally-nested blocks too. Requires a `.tox` rebuild, so deferred.

### 6.4 Per-kind args validation (`_validate_args`)

| kind | required args | optional args | TD endpoint |
|---|---|---|---|
| `create_node` | `op_type: str`, `name: str` | `x: float`, `y: float` | `POST node/create` (parent = `op.target`) |
| `set_params` | `params: dict[str, Any]` | — | `PATCH nodes/{target}/params` |
| `connect` | `from: str`, `to: str` | `from_output: int=0`, `to_input: int=0` | `POST node/connect` |
| `layout` | `x: float`, `y: float` | — | `PATCH nodes/{target}/position` |
| `annotate` | `text: str` | `color: [r,g,b]` | `POST node/create` (annotate COMP) |
| `macro` | `macro_type: str` | `prefix: str=""` | `POST macro/create` (parent = `op.target`) |

`_validate_args` raises `PatchOperationArgsError("op[{i}] kind={kind}: missing required arg '<name>'")` on any missing/extra/wrong-type key. Caught by the apply loop, recorded as `failed_op=i, failed_reason=...`. **Never reaches TD** — a mis-specified op never touches state.

### 6.5 Name-collision readback

When `create_node` runs, the TD response includes the actual created path (TD auto-suffixes on collisions: requested `noise1` may become `noise2`). The applier reads this back and stores it in `result.created_paths` — NOT the requested name. Subsequent `connect` ops that reference "the just-created noise" should index `created_paths`, not hardcode names.

This is the hidden ergonomic improvement: the LLM doesn't need to predict TD's suffixing logic.

### 6.6 Variants flow (`patch.generate_variants`)

```
rng = random.Random(seed or random_seed())
variants, skipped = [], []
for strategy in strategies:
  if strategy == "param_jitter":
    variants.extend(_apply_jitter(base, n, rng))   # numeric params × (1 + rng.uniform(-0.3, 0.3))
  elif strategy in ("operator_substitute", "topology_perturb"):
    skipped.append(f"{strategy} (not yet implemented)")
  else:
    raise ValueError(f"unknown strategy: {strategy}")
return variants[:n], skipped
```

Each generated variant gets: `base_plan_id = base.id`, `strategy = "param_jitter"`, `seed = <derived sub-seed>`. Two runs with the same seed produce identical variants.

## 7. Error handling

### 7.1 Failure-to-response mapping (`td_patch_apply`)

| Failure | Response | Caller action |
|---|---|---|
| Malformed plan dict (Pydantic validation) | `{success: False, error: "..."}` | Fix plan, re-call |
| Nested undo block (our sentinel) | `{success: False, error: "prior patch undo block still active; call td_project_lifecycle action=end_undo_block first"}` | End block, re-call |
| Nested undo block (external, undetectable) | Proceeds; `result.risk_flags` includes `"external-nested-block-possible"` | Caller decides |
| Op N fails (args or TD error) | `{success: True, result: {status: "broken", failed_op: N, failed_reason, applied_ops: [0..N-1], rollback_hint}}` | Call `td_project_lifecycle action=undo` to revert |
| All ops apply + validation errors | `{success: True, result: {status: "warnings", validation: {...}}}` | Caller inspects; may choose to undo |
| All ops apply + validation clean | `{success: True, result: {status: "clean", validation: {ok: true}}}` | Done |

### 7.2 Error taxonomy

- `PatchOperationArgsError` — args dict malformed (missing/extra/wrong-type keys). Caller fixes the dict.
- `TDRequestError` — TD returned an error response. Includes TD's error message. Caller checks preconditions.
- `TDConnectionError` — TD unreachable (network/process dead). Caller retries or surfaces.
- `NestedBlockError` — Python-side sentinel saw active block. Caller ends prior block.
- `UnknownStrategyError` (variants only) — unrecognized strategy name. Caller uses a valid strategy.

Warnings (do not fail the op, logged on result):
- `UnknownOpTypeWarning` — op_type not in knowledge corpus AND not in stock allowlist. Appears in `result.changed_params[i].warnings`. Same allowlist logic as existing `td_validate_recipe` / `td_audit_project`.

### 7.3 What `td_patch_apply` does NOT do

Explicit non-responsibilities:

- **Does not auto-rollback** on partial failure. Caller sees `status=broken` + `rollback_hint` and decides.
- **Does not take snapshots.** `before/after_snapshot_id` reserved for v1.5.1 auto-snapshot feature (matches §4.6 + §10 deferral).
- **Does not resolve `depends_on`.** v1.5.0 applies strictly in list order. The field is recorded for future reordering features.
- **Does not retry TD requests.** One attempt per op. `TDConnectionError` stops the loop.
- **Does not validate cook order.** If the LLM connects before setting params and that breaks cook, that's a design issue in the plan — surfaces as validation warnings, not an apply-time failure.

## 8. Testing strategy

Three layers, three test files, + one live smoke script.

### 8.1 Layer 1 — Model tests (`tests/models/test_patch_models.py`) — ~12 tests

Pure Pydantic validation, no TD, no MCP.
- `PatchOperation`: each kind parseable, `extra="forbid"` rejects unknown fields, `depends_on` defaults to `[]`.
- `PatchPlan`: `id` is valid UUID, `created_at` is UTC datetime, empty ops list valid, `source` Literal enforcement.
- `PatchVariant`: inherits all PatchPlan fields, `source` narrowed to `"variant"`, `base_plan_id/strategy/seed` required.
- `ValidationPlan` / `ValidationReport` / `PatchResult`: shape invariants, reserved None fields accept None.

### 8.2 Layer 2 — `patch/*` unit tests — ~27 tests (22 logic + 5 sentinel)

Fake TD client fixture at `tests/patch/conftest.py`:

```python
class FakeTDClient:
    def __init__(self, scripted=None):
        self.calls = []
        self.scripted = scripted or {}
    async def request(self, endpoint, params=None):
        self.calls.append((endpoint, params))
        if endpoint in self.scripted:
            resp = self.scripted[endpoint]
            if isinstance(resp, Exception): raise resp
            return resp
        return {}
```

**`tests/patch/test_planner.py`:**
- `build_plan(operations=...)` → `source="operations"`, ops preserved.
- `build_plan(recipe_id=...)` with stubbed store → `source="recipe"`.
- `build_plan(intent="feedback trail")` → matches `_INTENT_MACRO_KEYWORDS`, emits macro op.
- Precedence: `operations > recipe > intent` when multiple provided.
- None of three → `ValueError`.
- Unknown op_type → `required_ops` contains `"unknown:<type>"`.
- Risk flags: `>20 ops` → `"mass-change"`; `target_root="/"` → `"affects-root"`.

**`tests/patch/test_applier.py`:**
- Clean apply: 3-op plan → `status=clean`, all 3 in `applied_ops`.
- Op-N fails: scripted `TDRequestError` on op 2 of 4 → `status=broken, failed_op=2, applied_ops=[0,1]`; fake client recorded `end_undo_block` call.
- Bad args: missing required key → `PatchOperationArgsError`, `failed_op=0`, no TD calls.
- Nested-block refusal: sentinel preset → `NestedBlockError` before any TD call.
- Name-collision readback: scripted TD response with suffixed name → `created_paths` records actual path.
- `auto_validate=True` + errors present → `status` promoted from `clean` to `warnings`.

**`tests/patch/test_validator.py`:**
- Clean: empty errors → `ok=True`.
- With errors → `ok=False`.
- `capture_frames` non-empty → frame-capture call; empty → no capture call.

**`tests/patch/test_variants.py`:**
- `param_jitter` with fixed seed: two runs identical.
- Different seed: variants differ.
- `n=5` requested, 5 returned.
- `strategies=["operator_substitute"]` → empty variants + skipped note.
- `strategies=["unknown"]` → `ValueError`.
- Numeric params jittered within ±30%; non-numeric untouched.

**`tests/patch/test_undo_sentinel.py`:**
- Fresh `UndoBlockSentinel()` → `is_active() == False`, `active_label is None`.
- `mark_active("label")` → `is_active() == True`, `active_label == "label"`.
- `mark_active` called while already active → raises `RuntimeError`.
- `mark_inactive` → back to `False`.
- `mark_inactive` while inactive is a no-op (idempotent).

This isolates the sentinel semantics from the applier so the applier's own nested-block refusal test can focus on the `raise NestedBlockError` wiring.

### 8.3 Layer 3 — MCP tool behavioral tests (`tests/test_tools_patch.py`) — ~12 tests

Uses the existing MCP test harness. Full stack: `ctx → tool → applier → fake TD`.
- Each of 5 tools: happy path + one invalid-args path (10 tests).
- `td_patch_apply` broken outcome returns `success=True` with `result.status=broken` (envelope vs. outcome).
- `td_plan_patch` (legacy) still emits the old dict shape, driven by new internals.
- `td_preflight_patch` (legacy) still emits the old dict shape.
- Audit log called for every tool (check mock audit records).
- Telemetry counter bumped.

### 8.4 Lint-regression coverage (automatic)

- `tests/test_no_opaque_params_wrapper.py` (from Phase 1) — auto-catches if any new `td_patch_*` tool accidentally uses the opaque `params: InputModel` pattern.
- `tests/test_tools_schema_snapshot.py` — regenerated via `TDPILOT_UPDATE_SCHEMA=1` after adding the 5 new tools. 5 new schemas appear; 92 existing schemas unchanged (snapshot proves zero drift).

### 8.5 Live-TD smoke script (`scripts/patch_session_smoke.py`)

Manual invocation, not in CI. Requires TD running. End-to-end:

## 10. Scope boundaries

### In scope for v1.5.0

- 5 new MCP tools + 7 new Pydantic models (PatchOperation, PatchPlan, PatchPreview, ValidationPlan, ValidationReport, PatchResult, PatchVariant) + 5 internal modules (planner, applier, validator, variants, undo_sentinel) + 1 tools submodule.
- Legacy tool shim refactor (2 tools).
- Python-side undo-block sentinel.
- `param_jitter` variant strategy.
- Three-layer test suite (~46 tests).

### Deferred to v1.5.1 (tracked but out of scope now)

- Destructive op kinds: `delete`, `disconnect`, `set_content`, `exec_python`.
- TD-callback `project/lifecycle action=undo_block_status` endpoint.
- `operator_substitute` + `topology_perturb` variant strategies.
- Discriminated-union `PatchOperationArgs` models.
- Auto-snapshot on apply (populating `before/after_snapshot_id`).

### Out of scope indefinitely

- Server-side `PatchSessionStore` (statelessness is a design commitment).
- Rich LLM-driven intent parsing inside `td_patch_plan` (the MCP caller IS an LLM; duplicate intelligence rejected).
- Automatic rollback on `td_patch_apply` failure (caller decides).

## 12. Open questions

None blocking implementation. Two known tensions to revisit during the TDD loop:

1. **Nested-block detection granularity.** The Python-side sentinel misses externally-opened undo blocks. If this turns out to cause confused undo behavior in real usage, accelerate the v1.5.1 TD-callback endpoint.
2. **`args: dict` ergonomics.** If the per-kind runtime validation produces confusing error messages for LLM callers, graduate to discriminated unions earlier than v1.6.0.

Both will surface through test feedback; neither needs to be resolved before implementation.
