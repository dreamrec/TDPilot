# TDPilot v1.5.0 Implementation Plan

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship TDPilot v1.5.0 as a modular, safer, more creative TouchDesigner patching system — starting with the Bug A schema migration (69 opaque tools → rich schemas) and progressing through registry/models/TD-callback splits, a patch-session MVP, and a curated creative recipe pack.

**Architecture:** Four phases, each producing a working intermediate release. Phase 1 (Bug A) is mechanical and independent — the highest immediate user value. Phases 2–4 (module splits, patch sessions, recipes) are layered architecture work that benefits from Phase 1 being done first. The MCP surface stays at 92 tools throughout Phase 1–2; Phases 3–4 grow the surface deliberately.

**Tech Stack:** Python 3.11+, FastMCP (`mcp.server.fastmcp`), Pydantic v2, `Annotated[str, Field(...)]` for inline validation, pytest, ruff, uv. TD-side Python in `td_component_src/` bundled by `scripts/build_td_callbacks.py`.

**Starting state:** v1.4.7 shipped and tagged at `8b72f05` on `origin/main`. All 12 live-validation fixes from v1.4.6/v1.4.7 are in production. Repo has 594 passing tests, ruff clean. Bug A PoC (`td_delete_node`) landed in commit `2be9362` — proves the migration pattern works.

## Chunk 2: Phase 1 — Bug A schema migration (69 tools)

**Goal:** Rewrite every `async def td_foo(params: InputModel, ctx: Context)` signature to `async def td_foo(ctx: Context, ...explicit args...)` so MCP clients see flat, introspectable schemas instead of the opaque `params: {}` wrapper.

**Why this matters:**
- See `docs/superpowers/reports/2026-04-24-bug-a-opaque-params-investigation.md` for the full root cause — FastMCP wraps `params: Model` signatures under a `$ref` to a `$defs` entry, and MCP clients don't resolve the ref, so every field descriptor is lost.
- 5 of the 8 live-hunt bugs in v1.4.7 (`td_create_node`, `td_set_content`, `td_get_nodes`, `td_stream_top`, `td_audit_project`, etc.) were caused by callers not knowing the right field names. Fixing Bug A eliminates that class of friction entirely.

**Files:**
- Modify: `src/td_mcp/tool_registry.py` (69 tool signatures)
- Modify: `tests/fixtures/tool_schemas.json` (regenerate after each batch)
- Read: `src/td_mcp/models/_legacy.py` (source of truth for each Input model's fields)
- Reference: `src/td_mcp/tool_registry.py:2021–2049` (the `td_delete_node` PoC from v1.4.6 — study this for the exact rewrite pattern)

**Rewrite pattern (copy exactly from the PoC):**

```python
# BEFORE:
@mcp.tool(name="td_delete_node")
async def td_delete_node(params: DeleteNodeInput, ctx: Context) -> str:
    return await _forward(
        ctx, "td_delete_node", "node/delete",
        params.model_dump(), audit_event="td_delete_node",
    )

# AFTER:
@mcp.tool(name="td_delete_node")
async def td_delete_node(
    ctx: Context,
    path: Annotated[
        str,
        Field(
            description="Absolute path of the node to delete (e.g. '/project1/noise1')",
            min_length=1,
        ),
    ],
) -> str:
    """Delete a node by its absolute path."""
    return await _forward(
        ctx, "td_delete_node", "node/delete",
        {"path": path}, audit_event="td_delete_node",
    )
```

**The migration is mechanical per tool, but the batches matter:** rewriting all 69 at once would create an unreviewable diff. Break into 7 batches of ~10 tools each, grouped by domain. Each batch gets its own commit.

### Task 2.8: Post-migration hardening

- [ ] **Step 1: Add a lint-style regression test**

Create `tests/test_no_opaque_params_wrapper.py`:

```python
"""Lint-style regression: no MCP tool should reintroduce the opaque
`params: InputModel` signature pattern that Bug A ( v1.5.0) eliminated.

Each tool's MCP schema (as emitted by FastMCP's tool manager) must
have its argument properties at the top level, not wrapped in a single
`params` key that points at a `$ref`.
"""

from __future__ import annotations

import json

import td_mcp.tool_registry as registry


def test_no_tool_has_opaque_params_wrapper():
    tools = registry.mcp._tool_manager.list_tools()
    offenders = []
    for t in tools:
        schema = t.parameters
        props = schema.get("properties", {})
        if list(props.keys()) == ["params"] and "$ref" in json.dumps(props):
            offenders.append(t.name)
    assert not offenders, (
        f"These tools still use the pre-v1.5.0 opaque `params: InputModel` "
        f"pattern: {offenders}. Rewrite to explicit args. "
        f"See docs/superpowers/reports/2026-04-24-bug-a-opaque-params-investigation.md."
    )


def test_every_tool_schema_has_field_descriptions():
    """Schemas should describe what each field is for — the Bug A fix
    makes this possible for all 69 migrated tools."""
    tools = registry.mcp._tool_manager.list_tools()
    missing_descriptions = []
    for t in tools:
        props = t.parameters.get("properties", {})
        for field_name, field_spec in props.items():
            if isinstance(field_spec, dict) and not field_spec.get("description"):
                missing_descriptions.append(f"{t.name}.{field_name}")
    # Allow a small number of legacy no-description fields (resource tools,
    # zero-arg tools), but most tools should be described.
    assert len(missing_descriptions) < 20, (
        f"Too many fields without descriptions: {missing_descriptions[:20]} "
        f"(total {len(missing_descriptions)}). Each rewritten tool should "
        f"have Field(description=...) for every arg."
    )
```

## Chunk 4: Phase 3 — Patch Session MVP

**Goal:** Add first-class `td_patch_*` tools that wrap multi-step creative edits in a plan → preview → apply → validate → keep/revise/undo workflow, with structured result/variant support.

**Why this matters:**
- Current multi-step edits (create nodes + set params + connect + validate) are spelled out in each caller. That's repetitive, error-prone, and doesn't compose well.
- A patch session is the unit of creative iteration — the thing you save as a technique, undo atomically, and reapply as a variant.

**Models to add (`src/td_mcp/models/patch.py`):**

- `PatchPlan` — id, intent, target_root, operations[], required_ops[], risk_flags[], undo_label, validation_plan
- `PatchOperation` — kind (create_node | set_params | connect | layout | annotate | macro), target, args, depends_on[]
- `PatchResult` — status (clean | warnings | broken), created_paths, changed_params, validation, before_snapshot_id, after_snapshot_id, undo_label
- `PatchVariant` — derived from the same intent, with a different parameter/connection style

**Tools to add (5 new):**

- `td_patch_plan(intent: str, target_root: str) → PatchPlan`
- `td_patch_preview(plan: PatchPlan) → dict` (human-readable summary + risk flags)
- `td_patch_apply(plan: PatchPlan, label: str | None) → PatchResult` (one undo block, captures before/after snapshots, runs validation)
- `td_patch_validate(target_root: str) → dict` (errors + cook stats + optional frame capture)
- `td_patch_variations(intent: str, target_root: str, n: int) → list[PatchPlan]` (2-4 variants from same intent)

**Internal, reusable components** (don't need to be MCP tools, may live under `src/td_mcp/patch/`):

- `src/td_mcp/patch/planner.py` — intent → PatchPlan
- `src/td_mcp/patch/applier.py` — PatchPlan → TD operations inside an undo block
- `src/td_mcp/patch/validator.py` — PatchResult validation (errors, cooks, frames)
- `src/td_mcp/patch/variants.py` — PatchPlan → [PatchPlan, ...]

**Acceptance:**
- One end-to-end behavioral test with a fake TD client covering plan → preview → apply → validate → undo.
- One live-TD smoke script that creates, applies, and undoes a small visual patch.
- No schema churn for the existing 92 tools — 5 new tools bring the total to 97.
- Undo-block correctness verified: calling undo after a bad apply fully reverts state.

**Execute:** This is a new-feature phase, not a refactor. Use `@superpowers:brainstorming` first to clarify intent parsing and variant-generation heuristics before writing the plan. Then `@superpowers:writing-plans` to produce the detailed task plan.

## Appendix B: Why batch sizes matter

10-tool batches are optimized for three constraints:
1. **Review tractability** — a single commit should be readable in 10–15 minutes. 10 tool rewrites ≈ 10 × (5-line signature change + 1-line body change) ≈ 100 lines of meaningful diff.
2. **Rollback safety** — if Batch N breaks something, you revert one commit and keep N-1 green. Smaller batches = finer rollback granularity.
3. **Schema snapshot churn** — regenerating the snapshot once per batch (7 times total) means ~7 small diffs to review instead of one massive one.

If you're running in subagent-driven-development mode (@superpowers:subagent-driven-development), each batch can be a fresh subagent task with clean context. That's ~8 subagent dispatches for Phase 1 (7 batches + hardening). Plan accordingly.
